# ⚠️ Discrepancias — Documentación vs. Estado Real del Código

**Última actualización:** 2026-07-22

> Este documento existe porque el proyecto arrancó con una base de código Flutter/FastAPI ya construida por otro equipo/sprint anterior, y la arquitectura descrita en `01-Arquitectura.md` a `04-Arquitectura-Frontend.md` es la que **el equipo decidió como objetivo**, con las razones y decisiones ya documentadas ahí. Ese documento manda: es el diseño correcto y acordado. El código heredado que no coincide con él no es una alternativa válida — es trabajo pendiente de corregir, deuda técnica de una implementación que se hizo antes de (o sin seguir) la decisión de arquitectura.
>
> Regla general: **la documentación de arquitectura es la fuente de verdad.** Este archivo no existe para justificar el código actual, sino para que quede explícito qué le falta al código para alinearse con lo documentado, y así poder priorizar cerrar esas brechas. Si vas a tocar una parte del sistema listada aquí, el trabajo por defecto es acercar el código al objetivo documentado, no perpetuar la desviación — salvo que el equipo indique explícitamente lo contrario para esa tarea puntual.

## 0. Bug de seguridad encontrado y corregido en esta revisión

`Backend/.gitignore` tenía la regla `backend/.env` (minúscula) para ignorar el archivo de variables de entorno. Como ese `.gitignore` vive *dentro* de `Backend/`, sus patrones con `/` son relativos a esa misma carpeta — la regla en realidad buscaba `Backend/backend/.env` (una subcarpeta que no existe), **no** `Backend/.env` (el archivo real). Se verificó con `git check-ignore -v Backend/.env`: no coincidía, es decir, **`Backend/.env` con secretos reales (`JWT_SECRET_KEY`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, credenciales de `DATABASE_URL`) no estaba protegido contra un `git add` accidental** en este filesystem case-sensitive (Linux). El mismo problema afectaba a la regla `backend/data/`.

**Corregido en esta revisión:** la regla de `.env` se cambió a `.env` (sin el prefijo `backend/`), verificado con `git check-ignore`. La regla de datos pesados pasó primero a `data/` y **luego se ajustó otra vez a solo `*.csv`/`*.csv.gz`**, porque un `data/` a secas ignoraba la carpeta completa — justo cuando se agregó ahí `sectores.geojson` (ver §1, fila "Geometría de sectores"), que sí debe versionarse. Si alguien ya tiene un `.env` con secretos reales y en algún momento corrió `git add -A` o `git add .` antes de esta corrección, vale la pena revisar el historial de commits para confirmar que nunca se coló (`git log --all --full-history -- Backend/.env`); a la fecha de esta revisión no aparece commiteado ningún `.env`.

## 1. Backend

| Área | Objetivo — lo que manda (`03-Arquitectura-Backend.md`) | Código real — pendiente de alinear (`Backend/`) |
| --- | --- | --- |
| Fuente de datos de sensores | ClickHouse, capa **Plata** del pipeline Tángara (solo lectura, agregación resuelta por el backend — decisión actualizada 2026-07-22, Gold no existe y no se va a esperar) | PostgreSQL + PostGIS, tabla propia `sensor_readings` vía SQLAlchemy async |
| Persistencia | Backend sin estado propio, sin base de datos propia | Base de datos propia con 3 tablas (`sensor_readings`, `users`, `game_scores`), creadas automáticamente al arrancar (`create_tables()` en `main.py`) |
| Geometría de sectores | `sectores.geojson` estático + `shapely`, cargado en memoria al iniciar | **El archivo ya existe** (`Backend/data/sectores.geojson`, agregado en esta revisión — 22 comunas de Cali, fuente oficial IDESC/Alcaldía, WGS84 verificado; ver `06-Plan-de-Accion.md` §2.3). Lo que falta es el código: no hay `services/geo.py` que lo cargue, ni `SectorIndex`/point-in-polygon con `shapely`, ni noción de "sector" en el modelo de datos — solo `sensor_id` individual |
| Endpoints | `GET /sectors`, `GET /sectors/{id}`, `GET /risk/{sector}`, `GET /education` | `GET /sensors/latest`, `GET /sensors/{sensor_id}/history`, `WS /sensors/ws/live`, más stubs `GET /auth/status`, `GET /api/chatbot/status`, `GET /game/status` |
| Autenticación | Ninguna — acceso abierto, sin cuentas de usuario | Modelo `User` (email + password hash) y router `auth.py` ya existen como base para JWT, aunque el router es un stub sin lógica todavía |
| Alcance del servicio | Un único propósito: exponer datos de calidad del aire | Incluye módulos adicionales fuera del alcance descrito: **chatbot** (IA sobre los datos, dependencias `langchain`/`langchain-openai`/`langchain-anthropic` en `requirements.txt`) y **gamificación** (`GameScore`, puntajes de partidas) |
| Caché | Cache en memoria con TTL corto (`services/cache.py`, ej. `cachetools`) para absorber el polling | No existe capa de caché todavía |
| Variables de entorno | `CLICKHOUSE_HOST`, `CLICKHOUSE_PORT`, `CLICKHOUSE_USER`, `CLICKHOUSE_PASSWORD`, `CLICKHOUSE_DATABASE`, `CLICKHOUSE_SECURE` (nombres reales, ya actualizados en `03-Arquitectura-Backend.md` §6 tras verificar contra el cliente `clickhouse-connect` del pipeline) | `DATABASE_URL` (Postgres), `JWT_SECRET_KEY`, `JWT_ALGORITHM`, `JWT_EXPIRE_MINUTES`, `LLM_PROVIDER`, `ANTHROPIC_API_KEY`/`OPENAI_API_KEY`, `ENVIRONMENT` |
| Migraciones | No aplica (sin BD propia) | `alembic` está en `requirements.txt` pero no hay carpeta de migraciones configurada — las tablas se crean con `Base.metadata.create_all` directo, no con migraciones versionadas |
| **Catálogo sensor→sector/ubicación** | Implícito: el backend resuelve sector con `sectores.geojson` + coordenadas del sensor | El repo del pipeline **no expone ningún catálogo de metadatos de sensores** (nombre, lat/lon, comuna). Se buscó en otros repos del mismo mantenedor (`sebaxtian/tangara-api-mvp`) y sí existe un esquema pensado para esto (tabla `tangara` con FKs a `barrio`/`sector`/`comuna`), **pero está vacío donde importa** (las FKs `id_barrio`/`id_sector` de cada sensor están nulas) **y desactualizado** (snapshot del 2023-05-21, solo 25 sensores vs. los ~47-50 mencionados en otras fuentes, todos `online: 0`). Tampoco ninguno de esos catálogos (`comuna.json`, `sector.json`, etc.) tiene geometría/polígono — son solo tablas de nombre/código. El sitio público `tangara.chis.pa` tampoco expone catálogo de ubicaciones. **Conclusión: no existe un catálogo listo y vivo para reutilizar — EcoBytes debe construirlo.** La única pista geográfica viva es la columna `geo` (String, probablemente geohash) en `tangara_plata`, decodificable a lat/lon sin depender de ningún repo externo; el GeoJSON de comunas de Cali en sí es dato público de la ciudad (portal de datos abiertos) y ya está en el repo (`Backend/data/sectores.geojson`) |

**Por qué está desalineado:** el pipeline Tángara → ClickHouse que exige la arquitectura objetivo no estaba disponible/accesible en el momento en que se construyó este backend, así que se implementó una base de datos propia (Postgres + PostGIS) alimentada por ingesta de CSV (`scripts/ingest_csv.py`) como solución provisional. Esto no cambia el objetivo — la migración a ClickHouse sigue siendo lo que hay que construir; Postgres es el estado transitorio, no el destino. Los módulos de **chatbot** y **gamificación** tampoco están en el alcance documentado y deben tratarse como scope adicional a revisar con el equipo, no como parte del backend núcleo. La calibración de PM2.5 (`services/calibration.py`) sí se implementó según lo esperado, con la corrección por humedad de Dillo et al., y es la única pieza que no requiere corrección.

**Nota de cierre (2026-07-22) — decisión Gold vs. Plata ya no es una discrepancia:** este documento tenía una fila señalando que `03-Arquitectura-Backend.md` asumía incorrectamente que `tangara_gold` ya existía. Se verificó que `tangara_gold` está marcada como "planificada" en el repo del pipeline (`sebaxtian/clickhouse-tangara`) y, dado el cronograma de la hackathon, el equipo decidió no esperarla: **`01-Arquitectura.md` y `03-Arquitectura-Backend.md` ya se actualizaron** para documentar `tangara_plata` como la fuente definitiva, con agregación resuelta en el backend. Esa fila se elimina de aquí porque ya no hay desalineación entre doc y decisión — el detalle técnico (esquema real de columnas, vista materializada Bronce→Plata) queda en `06-Plan-de-Accion.md` §2.1.

**Nota — asimetría del módulo de gamificación:** el backend tiene el modelo `GameScore` (con FK a `User`) y el router `game.py` como base de un feature de gamificación, pero **no existe ninguna contraparte en el frontend** — no hay `features/game/` ni ninguna referencia a puntajes o juegos en todo `lib/`. Si el módulo de gamificación no está en el alcance documentado (y no lo está), no solo sobra el trabajo pendiente del backend: ya se invirtió esfuerzo en un modelo de datos y router que, al día de hoy, no tiene ningún consumidor y probablemente deba eliminarse en vez de completarse.

### 2.1 Deuda adicional encontrada dentro del propio frontend

Estos hallazgos no son "doc dice X, código tiene Y" directo, pero salieron al comparar el código contra la arquitectura objetivo y son bloqueantes para ejecutar limpiamente EPI-01/EPI-02 del backlog — hay que resolverlos como parte de la migración, no ignorarlos:

- **La ruta `/mapa` real muestra un mapa falso; el mapa real que sí existe está huérfano.** `MapaPage` (`features/dashboard/presentation/pages/map_page.dart`, la página que de verdad sirve `/mapa`) pinta un `Container` gris con `GridPaper` y el texto literal `"[ Espacio reservado para mapa interactivo ]"` — no es un mapa interactivo, es una maqueta estática con tarjetas flotantes y cifras hardcodeadas (AQI 55, "Zona Industrial", etc.). Mientras tanto, **sí existe** un componente de mapa real y funcional (`MapArea` en `features/dashboard/presentation/widgets/map_area.dart`, con `flutter_map` + tiles de OpenStreetMap + marcadores reales), pero su único consumidor es `DashboardPreviewSection`, una sección de marketing dentro de la **landing page** (`features/landing/presentation/widgets/dashboard_preview_section.dart`) — es decir, el mapa interactivo real se usa como imagen de vista previa en la página de aterrizaje, no como la pantalla funcional del producto. Migrar hacia el objetivo documentado implica reemplazar el contenido de `MapaPage` por (una versión conectada de) `MapArea`, no construir un mapa desde cero.
- **`SensorBloc` no está conectado a nada.** `sensor_bloc.dart`/`sensor_event.dart`/`sensor_state.dart` implementan el patrón Bloc completo (con un `TODO: reemplazar por SensorRepository remoto` explícito en el código), pero no hay ningún `BlocProvider`/`BlocBuilder` en toda la app que lo use — es andamiaje muerto, no una fuente de datos real para `MapaPage` ni para `MapArea`/`ControlSidebar`, que en la práctica ambos leen directo de `MockSensorRepository`.
- **El único test existente no prueba la app real.** `test/widget_test.dart` monta `EcoBytesApp` (definido en `lib/app.dart`), pero el entrypoint real de la app es `MyApp` en `lib/main.dart` (ver fila "Arranque de la app" arriba). El test pasa, pero no valida el árbol de widgets que corre en producción.
- **`landing/` no se puede borrar de forma aislada tal como está hoy.** `map_page.dart`, `learn_page.dart` y `chatbot_page.dart` importan directamente `LandingHeader`, `LandingFooter` y `LandingMobileNav` desde `features/landing/presentation/widgets/` para su cabecera y pie de página globales. Ejecutar la tarea `T-00.4` (eliminar landing) tal cual está en el backlog rompe la compilación de las otras tres páginas — antes de borrar `landing/`, `LandingHeader`/`LandingFooter`/`LandingMobileNav` deben moverse a `shared/widgets/` (son en realidad el header/footer global de toda la app, no widgets exclusivos de la landing).
- **El chatbot del frontend es una maqueta visual sin backend, y lo dice explícitamente en su propia UI:** el badge de estado en `chatbot_page.dart` muestra "Fuera de línea · Modo de demostración visual" — confirma que ni siquiera intenta llamar al router `chatbot.py` del backend (que de todas formas es un stub). Es puramente decorativo hoy.
- **Estadísticas inventadas presentadas como reales en la landing.** `StatsBar` (`features/landing/presentation/widgets/stats_bar.dart`) muestra "47 sensores activos", "22 comunas cubiertas" y "2.4M ciudadanos informados" como texto hardcodeado — el mismo patrón de dato falso disfrazado de real que el mapa de `MapaPage`, solo que aquí es contenido de marketing. Baja prioridad porque `landing/` está marcada para eliminación, pero si se decide conservar alguna sección de landing, estos números deben salir o marcarse explícitamente como ilustrativos.
- **Error tipográfico del nombre del equipo en el footer.** `landing_footer.dart` muestra "BitAVIT Labs" dos veces; el nombre correcto en toda la documentación (README, `01-Arquitectura.md`) es **Bit&Volt Labs**. Cosmético, pero visible en producción.

## 3. Contrato de API

Los docs (`03-Arquitectura-Backend.md` §7) asumen que backend y frontend ya pueden desarrollarse en paralelo contra un contrato fijo de 4 endpoints. En la realidad:

- El backend expone datos por **sensor individual**, no por **sector geográfico** — falta toda la capa de agregación por sector (mapeo sensor→sector, cálculo de `estado` verde/amarillo/rojo, umbral de "sin datos recientes").
- El frontend no consume el backend en absoluto todavía — el dashboard corre 100% sobre `MockSensorRepository`.
- No existe el endpoint de riesgo histórico (`/risk/{sector}`) ni en backend ni como necesidad consumida en frontend.

El contrato correcto es el ya documentado en `03-Arquitectura-Backend.md` §3 (`/sectors`, `/sectors/{id}`, `/risk/{sector}`, `/education`). El trabajo pendiente no es renegociar ese contrato a partir de lo que el backend ofrece hoy, sino construir la capa de sectorización (mapeo sensor→sector, cálculo de `estado`, umbral de "sin datos recientes") para que el backend pueda cumplirlo, y conectar el frontend a él en vez de a `MockSensorRepository`.

## 4. Cómo mantener este documento

- Cerrar una fila significa **corregir el código para que cumpla lo documentado**, no reinterpretar el documento a la luz del código. Cuando se ejecute una tarea del backlog que cierre una brecha (ej. `T-00.1` elimina carpetas nativas), **borra la fila correspondiente de este documento** en vez de dejarla como histórico — para eso está el historial de git.
- Si aparece una discrepancia nueva no listada aquí, agrégala con: qué dice el doc (el objetivo), qué hay en el código (la desviación), y por qué existe la desviación (si se conoce la razón) — nunca como justificación para no corregirla.
- La única forma legítima de eliminar una fila sin haber tocado el código es que el **equipo** decida explícitamente cambiar el objetivo (ej. quedarse con Postgres en vez de migrar a ClickHouse). En ese caso, la corrección correcta es actualizar primero `01-Arquitectura.md`/`03-Arquitectura-Backend.md` — porque esos documentos son la fuente de verdad — y solo después eliminar la fila de aquí. Nunca al revés: el código nunca redefine el objetivo por sí solo, ni por omisión ni porque "ya está así".
